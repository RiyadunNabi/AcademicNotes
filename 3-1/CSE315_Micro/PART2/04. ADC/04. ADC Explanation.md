## Key Takeaways

- An MCU is **digital**; it understands only binary values.
- Real-world quantities (temperature, light, sound, etc.) are **continuous (analog)**.
- Sensors convert physical quantities into electrical signals, usually voltages.
- The MCU still cannot directly understand those analog voltages.
- An **ADC (Analog-to-Digital Converter)** converts the analog voltage into a digital number the MCU can process.
- ADC is the essential bridge between the analog world and the digital microcontroller.

```
        │
        ▼
Microcontroller
```

## Key Takeaways

- **Sampling** approximates the **time (X-axis)** by taking measurements at regular intervals.
- **Quantization** approximates the **voltage (Y-axis)** by mapping each sample to one of a finite number of digital levels.
- **Step size (resolution)** = Voltage Range ÷ Number of ADC Levels.
- Increasing the ADC bit width (2-bit → 3-bit → 8-bit → 10-bit) decreases the step size and improves accuracy.
- A **digital input pin** only distinguishes LOW/HIGH, whereas an **ADC** measures the analog voltage and converts it into a digital value.

# Slide 27 – Read ADCL Before ADCH

This is one of the most important rules in AVR ADC programming.

The slide says:

> ADCL must be read first, then ADCH. 

Let's understand why.

---

# Imagine a Mailbox

Suppose the ADC keeps producing new values.

```text
Reading 1

↓

Reading 2

↓

Reading 3
```

If you're reading the registers while a new conversion finishes,

you might accidentally combine

```text
Old ADCH

+

New ADCL
```

which gives a completely wrong result.

---

To prevent this,

ATmega32 locks the registers.

---

# What Actually Happens?

Suppose

```text
Conversion Complete

↓

ADCL updated

ADCH updated
```

Now you start reading.

---

### Step 1

You read

```text
ADCL
```

Immediately,

the ADC **locks** both registers.

No new conversion result can overwrite them.

---

### Step 2

You read

```text
ADCH
```

Now you have the complete result from the **same conversion**.

Only after reading ADCH does the ADC unlock the registers.

Exactly as described on the slide. 

---

# Why Is This Lock Necessary?

Imagine this sequence.

```text
Conversion 1

↓

ADCL = 50

ADCH = 2
```

You read

```text
ADCL
```

Before reading ADCH,

another conversion finishes.

```text
Conversion 2

↓

ADCL = 80

ADCH = 3
```

Now you read ADCH.

Your final value becomes

```text
ADCL from Conversion 1

+

ADCH from Conversion 2
```

This value never actually existed!

The lock prevents exactly this problem.

---

# Important Note from the Slide

The slide also says:

If another conversion finishes **before ADCH is read**,

that new result is **lost** because the registers are locked until you complete the read. 

So don't delay after reading ADCL.

The slide asks

> Can you read only ADCH?

Answer:

**Yes**, if

```text

```

This is commonly used when 8-bit accuracy is enough.

---

# Can You Read Only ADCL?

The slide also asks

> Can you read only ADCL? 

Answer:

**No**, not if you want a valid ADC result.

Why?

Because:

- ADCL contains only part of the 10-bit value.
- Reading ADCL locks the registers.
- If you never read ADCH, the ADC stays locked and future conversion results cannot be transferred into the data registers.

So **ADCL alone is not useful**.

---

# Real-Life Example

Suppose you connect a potentiometer.

```text

↓

↓

```

### Method 1 (Full Accuracy)

```c

```

You get the complete 10-bit value.

---

### Method 2 (Fast, 8-bit)

Enable

```text
ADLAR = 1
```

Then simply

```c
value = ADCH;
```

Perfect for applications like LED brightness where full 10-bit precision isn't necessary.

---

# Complete Picture

```text
          ADC Conversion
                 │
                 ▼
          10-bit Result
                 │
      ┌──────────┴──────────┐
      ▼                     ▼
    ADCH                  ADCL

      └──────────┬──────────┘

        Read ADCL First
                 ▼

                 ▼

```

# Key Takeaways

- The ATmega32 ADC produces a **10-bit result**, so it is stored in **two 8-bit registers: ADCL and ADCH**.
- **ADLAR (Left Adjust Result)** changes how the 10-bit result is arranged, allowing quick **8-bit reads from ADCH**.
- For the **full 10-bit result**, always **read ADCL first, then ADCH**.
- Reading **ADCL locks** the data registers until **ADCH** is read, ensuring both bytes belong to the same conversion.
- If a new conversion finishes before ADCH is read, **that new result is discarded** because the registers remain locked.
- Reading **only ADCH** is acceptable **only when using left-adjusted results (ADLAR = 1)** and when 8-bit precision is sufficient.
- Reading **only ADCL** is not useful for obtaining a correct ADC result.
