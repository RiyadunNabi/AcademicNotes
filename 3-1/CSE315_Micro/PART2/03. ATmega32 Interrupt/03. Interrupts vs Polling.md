# Things you must remember

- **Interrupt request ≠ immediate execution.** The CPU first finishes the current instruction.
- **PC (Program Counter)** stores the address of the next instruction.
- Before entering the ISR, the CPU saves the current context (including the PC) so it can resume correctly afterward.
- The **stack** is temporary storage used during interrupt handling.
- The CPU changes the PC to point to the ISR, executes it, restores the saved context, and resumes the interrupted program exactly where it stopped.

# Things to remember

- **ATmega32 supports 21 interrupt sources** (16 commonly used in this course). 
- **External interrupts** come from outside the chip (`INT0`, `INT1`, `INT2`).
- Every interrupt has a **fixed vector (memory address)**.

- **Smaller vector number = higher priority.**
- `INT1_vect`, `INT0_vect`, etc., are **symbolic names** used in C to define ISR functions; the compiler links them to the correct vector table entry.

# Part 5: Why do we need `volatile`?

This is probably the most important viva topic.

The slides discuss it in detail. 

---

Suppose

```c

```

```c

{
    tick++;
}
```

Main

```c

{
}
```

Looks correct.

But sometimes

it never exits the loop.

Why?

---

# Compiler Optimization

Compilers try to make programs faster.

Suppose

```c
while(tick==0)
{
}
```

Compiler looks.

It says

```
Inside this loop,

nothing changes tick.
```

So it thinks

```
tick will always remain zero.
```

Then it may optimize the code into something equivalent to

```
Infinite loop.
```

Because **the compiler doesn't know an ISR can change `tick`**.

---

# But ISR Changes It!

Imagine

```
Main

↓

tick = 0

↓

Loop forever
```

Interrupt occurs

```
tick++

↓

tick becomes 1
```

Program should leave the loop.

But compiler had already assumed

```
tick never changes.
```

Bug!

---

# Solution

Declare

```c
volatile uint8_t tick;
```

Now compiler is told

> "Do NOT assume this variable stays the same. It may change unexpectedly."

The slide's example uses exactly this idea. 

---

# What does `volatile` really mean?

It **doesn't** make the variable faster.

It **doesn't** protect it.

It simply tells the compiler:

```
Read this variable from memory every time.

Don't cache it.

Don't optimize away accesses.
```

---

# Real-life Analogy

Imagine a digital scoreboard.

Without `volatile`

You look once.

```
Score = 10
```

Then you never look again because you assume it won't change.

But someone else updates it to

```
11
```

You'll never notice.

With `volatile`

You check the scoreboard every time.

So you'll always see the latest value.

---

# Complete Flow

```

↓

↓

↓

↓

↓

↓

```

# Things to Remember

- `cli()` disables **all** interrupts globally by clearing the global interrupt enable bit. 
- When an ISR starts, ATmega32 **automatically disables further interrupts** by clearing the global interrupt flag.
- `RETI` returns from the ISR and automatically re-enables global interrupts.
- Keep ISRs **short and fast**; let the main loop do heavy work.
- Variables shared between `main()` and an ISR should usually be declared **`volatile`** so the compiler always reads their current value.

# Viva Questions

### Q1. Why do we use `cli()`?

**Answer:** To temporarily disable all interrupts during critical operations that must not be interrupted.

---

### Q2. Why are interrupts automatically disabled inside an ISR?

**Answer:** To prevent another interrupt from interrupting the current ISR (nested interrupts are disabled by default).

---

### Q3. Why should an ISR be short?

**Answer:** A long ISR delays other interrupts and can cause missed events or poor system responsiveness.

---

### Q4. Why is `volatile` used?

**Answer:** Because variables modified by an ISR can change unexpectedly. `volatile` prevents the compiler from optimizing away reads/writes to those variables.
